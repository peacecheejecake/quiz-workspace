# SEARCH-01 — 통합 검색 (문제·다국어 본문)

**상태:** 확정 화면 요구사항 v1.3 · UX3c 개정 2026-10-20 (Workspace header 통합 검색) · UX4 개정 2026-10-21 (검색 옵션 단일 목록) · UX6 개정 2026-10-28 (문제·본문 검색 범위 분리와 on/off)
**Route:** `/workspaces/:workspaceId?q=:query` (Workspace 홈 header; 이전 `/workspaces/:workspaceId/search?…`는 `scope=content`로 redirect)
**테스트:** `tests/e2e/search/search.spec.ts`
**연계:** [전체 아키텍처](../architecture.md), [디자인 시스템](../design-system.md), [E2E 규칙](../e2e-strategy.md)

## 레이아웃 및 컴포넌트
- Dense / BM25 / Hybrid·RRF와 Reranker를 선택할 수 있는 검색 옵션을 제공한다. 검색 API는 server-side workspace filters와 SourceLocation(페이지·block ID·revision)을 반환한다.
- API와 화면은 owner / viewer / 로그인 상태에 따라 기능과 데이터 표시 범위를 구분한다.
- 모든 편집·상태 변경은 서버 측 인가·revision 일관성을 검증한다.
- "검색 방식"(키워드/의미/하이브리드) 선택지의 설명은 Tooltip으로 보여 준다(hover·키보드 focus, `aria-describedby` 유지, hover 없는 기기는 인라인; UX1 2026-10-19, design-system.md §4.1).
- query embedding을 쓸 수 없으면 키워드(BM25) 결과로 계속 검색하고 비차단 안내를 표시한다(AC06).

## 통합 검색 (UX3c 2026-10-20)

- 문제 검색과 본문(내용) 검색을 하나로 합친 검색창이 Workspace 홈 header 맨 위에 있다. 입력란(접근성 이름 "검색어") + 검색 아이콘 버튼(접근성 이름 "검색", 글자 없음). Enter도 검색한다.
- 검색창 바로 아래에 **검색 범위** 체크박스 두 개 `문제`·`본문`이 있다(UX6 2026-10-28; 이전 "검색 옵션" popover와 그 안의 `문제`·`내용` 체크박스를 대체한다). 각 체크박스 옆의 작은 글씨 텍스트 버튼 "설정"(접근성 이름 "문제 설정"·"본문 설정")이 그 범위의 상세 설정을 담은 popover를 연다. Hover tooltip이 아니라 Radix Popover라서 클릭·탭·키보드(Enter/Space)로 열리고(`aria-expanded`), Escape·바깥 클릭으로 닫히며 focus는 버튼으로 돌아간다. Popover 이름은 "문제 검색 설정"·"본문 검색 설정"이다.
  - **문제 설정**: Heatmap의 챕터·유형 필터.
  - **본문 설정**: 검색 방식(키워드/의미/하이브리드, 설명 tooltip)·문서·장.
  - 설정 버튼은 체크박스가 꺼져 있어도 열 수 있다(미리 설정해 둘 수 있다). 바꾼 설정은 마지막 검색에 바로 적용된다.
  - 문제지 PDF 검색은 별도 토글이 없다(UX4 유지): `문제`도 켜져 있으면 본문 검색이 문제지 PDF도 함께 검색하고(`papers=1`), `본문`만이면 책 문서만 검색한다(문서 필터에도 문제지가 나오지 않는다).
- 두 체크박스는 서로 독립이며 둘 다 끌 수 있다(이전 "마지막 하나는 끌 수 없다" 규칙 폐지). 체크박스를 바꾸면 마지막 검색에 바로 적용된다. 기본값은 둘 다 켜짐이다. 내용이 없는 범위도 체크박스는 켜고 끌 수 있고 기본값도 같다(화면이 저절로 체크를 바꾸지 않아 선택이 예측 가능하다); 대신 아래 규칙으로 검색 버튼과 안내가 상태를 알린다.
- **검색할 대상**: `문제` = 이 Workspace의 확정 문제(필터 없는 Heatmap에 문제가 하나 이상). `본문` = 발행본이 있는 책 문서, 그리고 `문제`도 켜져 있으면 발행본이 있는 문제지 PDF. 처리 중이라 발행본이 없는 문서는 세지 않는다. 문제 수나 문서 목록을 불러오지 못했으면 있다고 본다(검색을 막지 않는다).
- **검색 버튼 비활성화**와 안내(UX6): 아래 경우 검색 아이콘 버튼은 `disabled`이고(Enter도 검색하지 않는다) 버튼 옆 범위 체크박스 아래에 상태 메시지(`role="status"`, 텍스트)가 보이며 버튼의 `aria-describedby`가 그 메시지를 가리킨다. 비활성 버튼은 hover·focus를 받지 못하므로 tooltip만으로 알리지 않는다. 우선순위 순서:
  1. 둘 다 꺼짐: "검색 범위를 하나 이상 선택하세요."
  2. Workspace에 문제도 본문도 없음: "검색할 문제와 본문이 없습니다. 문서나 문제를 먼저 등록하세요."
  3. `문제`만 켜졌는데 문제가 없음: "검색할 문제가 없습니다. 문제를 먼저 등록하세요."
  4. `본문`만 켜졌는데 본문이 없음: "검색할 본문이 없습니다. 문서를 먼저 등록하고 발행하세요."
- 둘 다 켜졌는데 한쪽만 내용이 있으면 검색 버튼은 활성이고 **내용이 있는 쪽만 검색한다**. 같은 자리에 비차단 안내 "등록된 문제가 없어 본문만 검색합니다." / "검색할 본문이 없어 문제만 검색합니다."를 보인다(본문이 없으면 본문 검색 API를 부르지 않고 본문 결과 영역도 없다).
- 범위 `문제`: 홈의 문제 Heatmap을 검색어로 거른다(기존 QOV-01 검색). `본문`: header 아래 "본문 검색 결과" 영역(UX6에서 "원문 검색 결과"에서 이름 변경)에 결과 목록과 발췌 panel(AC01~AC06)이 나타나고, "검색 결과 닫기"로 검색어를 지우고 문제 화면으로 돌아간다. 둘 다: 둘 다. 둘 다 꺼지면 Heatmap은 거르지 않고 본문 결과도 없다.
- 상태는 URL에 둔다: `q`, `scope`(`questions`|`content`|`none`, 생략 = 둘 다; `content` = 본문, `none` = 둘 다 꺼짐 — UX6), 본문 검색 `mode`·`document`·`section`(장)·`papers=1`(검색 범위에서 정해지는 값, UX4), 문제 필터 `chapter`·`type`·`status`·`favorite`·`retry`. 새로 고침·뒤로가기·공유 링크로 같은 검색을 다시 연다. 이전 `/search?q=&mode=&document=&chapter=&papers=1`은 `scope=content`와 `section=`(← `chapter`)으로 옮겨 redirect한다.
- 검색 API(`POST /workspaces/:id/search`)는 본문(문서 chunk)만 검색하므로 범위 파라미터가 없다: `문제` 검색은 Heatmap(`questions/overview?q=`)이 맡고, 범위 선택은 어느 API를 부를지만 정한다. 서버 인가 규칙은 그대로다.
- 공유 보기(WS-VIEW-01)의 검색은 본문 검색만 있고 설정이 없으므로 범위 체크박스를 두지 않는다.

## 수용 기준

### SEARCH-01-AC01

- **Given:** 해당 화면과 테스트용 데이터 및 권한이 주어진 상태
- **When:** 관련 조작/네트워크 요청을 수행
- **Then:** 한국어 질문으로 영어 교재에 대한 의미 검색 시 관련 영어 본문과 PDF 페이지를 표시한다.

### SEARCH-01-AC02

- **Given:** 해당 화면과 테스트용 데이터 및 권한이 주어진 상태
- **When:** 관련 조작/네트워크 요청을 수행
- **Then:** 문서·장 필터를 선택하면 서버가 해당 범위만 검색하여 반환한다.

### SEARCH-01-AC03

- **Given:** 해당 화면과 테스트용 데이터 및 권한이 주어진 상태
- **When:** 관련 조작/네트워크 요청을 수행
- **Then:** 검색 결과에서 발췌를 선택하면 해당 PDF 페이지와 연결된 원문을 연다.

### SEARCH-01-AC04

- **Given:** 해당 화면과 테스트용 데이터 및 권한이 주어진 상태
- **When:** 관련 조작/네트워크 요청을 수행
- **Then:** 검색 결과가 없으면 명확한 빈 상태와 검색 수정 안내를 표시한다.

### SEARCH-01-AC05

- **Given:** 해당 화면과 테스트용 데이터 및 권한이 주어진 상태
- **When:** 관련 조작/네트워크 요청을 수행
- **Then:** 다른 사용자의 Workspace 검색 API를 직접 호출해도 문서 내용이 노출되지 않는다.

### SEARCH-01-AC07

- **Given:** 확정 문제와 발행된 문서가 있는 Workspace 홈(비활성화 경우는 문제·문서가 없거나 한쪽만 있는 Workspace)
- **When:** header의 통합 검색창에 검색어를 입력하고 검색 아이콘 버튼(또는 Enter)으로 검색하고, 검색창 아래 `문제`·`본문` 체크박스와 각 "설정" 버튼으로 범위와 상세 설정을 바꿈
- **Then:** 검색 버튼은 아이콘만 보이고 접근성 이름은 "검색"이다. 검색창 아래에 체크박스 `문제`·`본문`(기본 둘 다 켜짐)이 바로 보이고 "검색 옵션" 버튼은 없다. 각 체크박스 옆 "설정" 버튼(이름 "문제 설정"·"본문 설정")은 클릭과 키보드로 그 범위의 상세 설정 popover("문제 검색 설정": 챕터·유형 / "본문 검색 설정": 검색 방식·문서·장)를 열고 닫는다(`aria-expanded`, Escape로 닫히면 focus 복귀). "문제지 PDF도 검색" 토글은 없고, `문제`도 켜져 있으면 본문 검색이 문제지 PDF도 검색한다(UX4). 둘 다 켜지면 Heatmap이 검색어로 걸러지고 본문 검색 결과 영역도 나타난다. `문제`만이면 본문 결과 영역이 없고, `본문`만이면 Heatmap은 거르지 않은 채 본문 결과만 나타난다. 둘 다 끄거나, 켠 범위에 검색할 내용이 없거나(`문제`만인데 문제 없음, `본문`만인데 발행된 문서 없음), Workspace에 둘 다 없으면 검색 버튼이 비활성화되고 그 이유를 버튼의 `aria-describedby`로 연결된 상태 메시지로 보인다. 둘 다 켜졌는데 한쪽만 내용이 있으면 그쪽만 검색한다는 안내와 함께 검색한다. 검색 상태(`q`, `scope`, 설정)는 URL에 남아 새로 고침해도 같은 결과를 보이며, "검색 결과 닫기"는 검색어와 본문 결과를 지운다(UX3c, UX6).

### SEARCH-01-AC06

- **Given:** 문서가 색인된 Workspace에서 query embedding(dense) 공급자를 일시적으로 쓸 수 없는 상태(hosted embedder 장애·quota 초과·timeout; 테스트는 `APP_ENV=test` 실패 marker로 재현)
- **When:** 하이브리드 또는 의미 검색을 실행
- **Then:** 검색은 실패(503)하지 않고 BM25 키워드 결과만 반환하며, API 응답은 `degraded: ["dense_unavailable"]`을 담고, 화면은 결과 위에 차단하지 않는 안내 "의미 검색을 일시적으로 사용할 수 없어 키워드 결과만 표시합니다"를 `role="status"`(텍스트, 색만으로 구분하지 않음)로 표시한다. 정상 상태의 같은 검색에는 안내도 `degraded`도 없다.

## 검색 저하(dense 불가) 규칙 (M7.4b)

- 적용 범위: query를 embedding하는 단계의 장애만(`EmbeddingUnavailableError`: hosted embedder의 429·5xx·timeout·연결 실패·quota 초과). Qdrant 자체 장애는 기존대로 503.
- `hybrid`: BM25 목록만으로 결과(점수 유형 `bm25`). `semantic`: 같은 BM25 결과로 대체(의미 검색 결과가 아님을 안내 문구로 알린다). `keyword`: 영향 없음.
- 응답 `degraded`는 저하 코드 목록(현재 `dense_unavailable`만). `warnings`와 별개로, 클라이언트는 코드로 판단한다.
- 서버는 WARNING 로그 한 줄(예외 type과 code만)을 남기고 검색어·문서 원문·token은 남기지 않는다.
- 공유 보기(`WS-SHARE-VIEW`)의 검색도 같은 API 경로를 쓰므로 같은 응답 필드를 받는다.

## Test-first 규칙
- 위 AC ID를 Playwright test title에 포함하고 RED를 확인한 다음 API/UI를 구현한다.
